# Как выпускается версия

Правила проекта, чтобы релиз не приходилось собирать по памяти.

## Два языка, русский главный

Всё, что читает человек, ведётся на двух языках:

| Русский | English |
|---|---|
| `README.md` | `README.en.md` |
| `CHANGELOG.md` | `CHANGELOG.en.md` |
| `lang.sh` — блок `ru` | `lang.sh` — блок `en` |
| `MSG["ru"]` в `shaperctl.py` | `MSG["en"]` в `shaperctl.py` |

Русская версия основная: GitHub показывает `README.md`, и на неё ссылается
переключатель языка. Английская — перевод, а не отдельный текст: если правка
попала в один файл, она обязана попасть и во второй.

Строки интерфейса сверяются автоматически — CI падает, если в `ru` и `en`
разный набор ключей.

## CHANGELOG — это и есть release notes

Раздел версии в `CHANGELOG.md` пишется так, чтобы его можно было скопировать
в GitHub Releases без единой правки. Отдельного текста «для релиза» не
существует: он бы разошёлся с историей на второй же версии.

Значит, раздел версии должен отвечать на три вопроса:

1. **Что изменилось** — списком, самое заметное первым.
2. **Почему это было нужно** — одной фразой на пункт. «Исправлено X» без
   объяснения через полгода не расшифрует и автор.
3. **Что будет при обновлении** — последняя строка про сохранность настроек.

Технические подробности, интересные только автору, живут в комментариях кода,
а не здесь.

## Чек-лист выпуска

1. Поднять номер в `VERSION`.
2. Дописать раздел в `CHANGELOG.md` **и** `CHANGELOG.en.md`.
3. Обновить бейдж и заголовок в `README.md` и `README.en.md`.
4. Прогнать тесты (`tests/`), они же прогонятся в CI.
5. Залить файлы в репозиторий.
6. Releases → новый тег `vX.Y` → заголовок `vX.Y` → в тело скопировать раздел
   из `CHANGELOG.md`.

Пункты 1–3 проверяет CI: если версия не совпала хотя бы в одном из пяти
файлов, сборка падает.

## Нумерация

`X.Y`, без третьего числа.

- **Y** — обычный выпуск: новая возможность, исправление, переоформление.
- **X** — когда меняется устройство, а не поведение: появление API, смена
  формата данных на диске, отказ от чего-то старого.

Ломающих изменений в настройках и файлах состояния мы стараемся не делать
вовсе: на десятках нод любая миграция — это десятки шансов ошибиться.
